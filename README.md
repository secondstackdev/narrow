# Shape Ship v6

A methodology harness for building software with Claude Code, based on Basecamp's Shape Up framework. Five commands, a multi-model agent pipeline, deterministic verification via hooks, and a complete design workflow.

## What's New in v6

v6 closes five gaps surfaced by running v5: loose shaping with no model diversity, blank architecture/NFRs leaving scopes unbounded, QA that reviewed source instead of executing the app, QA that drifted happy-path, and tech decisions made from memory instead of surveying current options.

| Change | Where | What it does |
|--------|-------|-------------|
| Architect agent | `.claude/agents/architect.md` | Opus 4.8 — synthesises architecture proposals with weighed alternatives, runner-up rationale, and NFR impact |
| Red-teamer agent | `.claude/agents/red-teamer.md` | Sonnet 4.6 — adversarial review at Checkpoint 2.5 and inside `/qa`; different model from producers for blind-spot diversity |
| Researcher scout mode | `.claude/agents/researcher.md` | Surveys current options for load-bearing tech decisions during `/shape` (does not pick) |
| Architecture bootstrap | `.claude/commands/shape.md` | `/shape --architecture` defines `architecture.md` + NFRs; a gate blocks normal `/shape` until they exist |
| Scout → architect pitch flow | `.claude/commands/shape.md` | Phase B proposes architecture via survey + synthesis, not orchestrator memory |
| Executing QA | `.claude/commands/qa.md` | Functional Execution phase drives the running app through every pitch scenario via Playwright / API |
| Adversarial QA | `.claude/commands/qa.md` | Red-Team phase surfaces unhappy paths; the orchestrator executes each one |
| App launcher | `run.sh` | Long-running launcher with seeded state for QA execution — separate from the `verify.sh` gate |
| Per-scope cost estimate | `work.md` → scope JSON, `retro.md` | `/work` records approximate session-attributed cost into the scope's `cost_estimate`; `/retro` flags outlier scopes |
| Model assignment table | `CLAUDE.md` | Documents which model runs each phase and why |

### What's unchanged from v5

The four-agent implementation pipeline (researcher → reviewer → implementer → verifier), worktree isolation, hooks (PostToolUse formatting, Stop verification), cycle learnings, retro graduation, and `scope_type` routing all remain.

## Quick Start

1. **Copy Shape Ship v6 files** into your project root.
2. **Edit `CLAUDE.md`** with your project's stack, NFRs, and constraints.
3. **Edit `product.md`** with your product vision and users.
4. **Run `/shape --architecture`** to bootstrap `architecture.md` and NFRs (one-time; `/shape` blocks until this is done).
5. **Run `/shape --brand`** to create your design system in `brand.md`.
6. **Configure `verify.sh`** (the pre-commit/CI gate) and `run.sh` (the app launcher with seeded state for QA) for your toolchain.
7. **Run `/shape`** with your first idea to produce a pitch.
8. **Run `/work`** to build scopes through the pipeline.
9. **Run `/qa`** in a fresh session to review the build.

**Functional QA in `/qa`:** Playwright MCP ships configured in `.mcp.json` and loads with the session. For `frontend` / `full-stack` scopes, `/qa` is a hard gate — it drives the running app (launched via `run.sh`) through every pitch scenario and every adversarial probe. There is no manual-review fallback for these scope types (that was the v5 escape hatch that let unhappy-path gaps ship). `backend` / `infra` scopes execute via direct API/CLI calls instead of Playwright.

## Commands

### `/shape` — Shape a raw idea into a buildable pitch

Three-phase conversation with three human checkpoints.
- Phase A: Problem, appetite, viability challenge (Checkpoint 1)
- Phase B: Solution, visual breadboards, architecture, test scenarios (Checkpoint 2)
- Phase C: Pitch, scope decomposition (Checkpoint 3)

**Brand mode (`/shape --brand`):** One-time creation of `brand.md` design system.

### `/work` — Build a scope (orchestrated pipeline)

Coordinates four agents:

```
researcher → 🛑 checkpoint → reviewer → 🛑 checkpoint → implementer → verifier → 🛑 checkpoint
```

Lightweight route for bug fixes (skips researcher/reviewer). Spike route for investigation-only work.

### `/qa` — Quality review a built scope

Independent session. Spawns verifier for automated checks first, then performs qualitative review: functionality against pitch scenarios, design compliance against `brand.md` and approved mockup, security assessment.

### `/retro` — Cycle retrospective and knowledge graduation

Run once at the end of a cycle, after all scopes are done and QA is complete.

Gathers all cycle learnings, progress notes, and QA findings, then proposes concrete updates to project configuration files (CLAUDE.md, agent definitions, brand.md, skills, verify.sh). Presents all proposals to the human before touching any file — every change requires explicit approval. Applied changes are committed individually and recorded in a permanent `retro.md` summary. Items identified as useful for the next cycle are written to `cycles/_seeds.md` and automatically promoted when the next cycle's first session starts.

## Agent Pipeline

The v5 pipeline enforces separation of concerns through tool restrictions:

| Agent | Can | Cannot |
|-------|-----|--------|
| researcher | Read, Grep, Glob, Bash(find/wc/git log), context7 | Edit, Write, Bash(test/run) |
| reviewer | Read, Grep, Glob | Edit, Write, Bash, context7 |
| implementer | Read, Edit, Write, Bash(test/run/git), context7 | git push, edit CLAUDE.md |
| verifier | Read, Bash(verify.sh/test/lint) | Edit, Write, context7 |

The reviewer that can edit will start fixing instead of flagging. The verifier that can edit won't give an independent assessment.

**Note on enforcement:** The `tools:` field in agent frontmatter strongly restricts which tools each agent will use, but this is enforced by instruction-following rather than a hard runtime boundary. Compliance is high but not deterministic. As Claude Code's agent runtime evolves, true structural enforcement will be tracked and noted here.

## Hooks

Two hooks are configured in `.claude/settings.json`:

- **PostToolUse (Edit/Write):** Auto-formats the file after every write using Prettier (requires `npx` + Prettier in the project). Silently skips if not available. For other stacks see the comment in `settings.json` for Python/Go/Rust alternatives.
- **Stop (`.claude/hooks/stop.sh`):** Runs `./verify.sh` at the end of every turn and surfaces output so failures are visible immediately. Also checks whether source files committed in the last turn were committed without updating their co-located `AGENTS.md` — a lightweight doc-drift signal. Always exits 0 (advisory).

These turn CLAUDE.md instructions like "always run the linter" from ~80% compliance into 100%.

## Cycle Learnings

Each cycle has a `learnings/` directory with three files that accumulate during the cycle:

- **conventions.md** — patterns all implementers should follow
- **gotchas.md** — traps and non-obvious behaviours to avoid
- **decisions.md** — architectural decisions with rationale

The researcher reads these at the start of each scope. The implementer updates them at the end of each session. By scope 5 of a cycle, the implementer knows what scope 1 learned — preventing the same mistakes from repeating.

## Agent Models

All agents default to `claude-sonnet-4-6` for cost efficiency. Sonnet handles research, review, and verification well. For complex implementation scopes, you can upgrade the implementer to Opus by editing the `model:` field in `.claude/agents/implementer.md`. The researcher and reviewer rarely need it.

---

## Multi-Person Teams

Shape Ship is designed for a single human + Claude workflow, but works with multiple developers:

- **Each developer works on a separate branch** for their scope (already implied by the git protocol)
- **Learnings files may have merge conflicts** — resolve by keeping both entries, never discarding either
- **Progress notes are append-only** — they merge cleanly without conflicts
- **Scope JSONs should not be edited by two people simultaneously** — coordinate scope ownership
- **Never merge another developer's scope without running `/qa` yourself** in a fresh session
